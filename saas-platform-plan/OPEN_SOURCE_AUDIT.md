# OPEN_SOURCE_AUDIT.md — Лицензии и пригодность для коммерческого SaaS

Дата: 2026-10-12. ✔ = подтверждено в этой сессии (источник) · ⚠ = из общих знаний, **обязательно перечитать файл LICENSE в репозитории перед использованием** · ❓ = гипотеза.
Это инженерный анализ, не юридическая консультация.

## 1. Ключевые принципы

- **GPL-3.0**: если вы *распространяете* программу (Windows-инсталлятор, Android APK), производная работа обязана быть под GPL. Для чисто серверного SaaS распространения нет, но смешивать GPL-код в одном процессе с закрытым кодом рискованно. Запуск отдельным процессом (CLI) обычно считается «совокупностью», но это спорная зона.
- **AGPL-3.0**: расширяет GPL на *сетевое взаимодействие*: если пользователи работают с изменённой версией по сети, вы обязаны предложить им исходный код *всего* приложения, включающего AGPL-компонент. Для закрытого SaaS это прямой конфликт. Либо открываем исходники всего сервиса, либо покупаем коммерческую лицензию, либо не используем.
- **Permissive (MIT, BSD, Apache-2.0, MPL-2.0)**: подходят. Apache/BSD/MIT — сохранить уведомления; MPL-2.0 — изменения самих MPL-файлов нужно публиковать, остальной код остаётся вашим.
- **Модельные лицензии** (веса нейросетей) — отдельная проверка: CC-BY-NC = *запрещено коммерчески*.

## 3. Вывод

- Весь основной стек (pypdf/pikepdf/qpdf/pdf-lib/PDF.js/PDFium/Tesseract/LibreOffice/PaddleOCR/OpenCV) — permissive/MPL, подходит для закрытого коммерческого SaaS.
- **Три запрета на старте:** PyMuPDF/MuPDF/Ghostscript (AGPL), PDFMathTranslate (AGPL), manga-image-translator (GPL), NLLB (CC-BY-NC).
- Если вы решите открыть исходный код всего сервиса под AGPL (стратегия open-core/«прозрачность»), то PyMuPDF становится допустимым — но вы теряете защиту от копирования конкурентами. Это стратегическое решение владельца.
- Перед каждым релизом: автоматический скрипт `license-scan` (pip-licenses / license-checker) + файл `THIRD_PARTY_NOTICES`.
